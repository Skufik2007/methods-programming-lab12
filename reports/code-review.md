# Code review кода, сгенерированного ИИ

Код приложения получен от отдельного экземпляра модели по промптам из
[`prompts/task1-webapp`](../prompts/task1-webapp). Сначала каждый ответ коммитится
без правок (коммиты с пометкой «без правок»), затем идут ревью, запуск, тесты и
исправления отдельными коммитами. Ниже перечислены реальные проблемы, найденные
при проверке. Формат каждой записи: что сгенерировал ИИ → в чём проблема → как исправил.

## 1. Зависимость от базы часовых поясов не объявлена

**Что сгенерировал ИИ.** В `app/config.py` валидатор `CLINIC_TIMEZONE` вызывает
`ZoneInfo("Europe/Moscow")`. Список зависимостей модель не дала: про пакет `tzdata`
сказано одной фразой в «Допущениях» в конце ответа.

**В чём проблема.** На Windows у `zoneinfo` нет системной базы IANA. Первый запуск
дымовой проверки упал ещё при импорте `app.db`:

```text
pydantic_core.ValidationError: 1 validation error for Settings
clinic_timezone
  Value error, unknown IANA time zone: 'Europe/Moscow'
```

Текст ошибки уводит в сторону: кажется, что неверно задана настройка, хотя на самом
деле не установлена зависимость. Та же ошибка возникнет в любом окружении без
системной базы часовых поясов, например в минимальном контейнере.

**Как исправил.** Добавил `tzdata` в обязательные зависимости `pyproject.toml` с
комментарием о причине. Предупреждение в «Допущениях» легко пропустить, а
зависимость в манифесте сработает всегда.

## 2. Дата у границы диапазона роняет сервер (500)

**Что сгенерировал ИИ.** В `app/schemas.py` (P1) тип `UTCDatetime` переводит любое
aware-значение в UTC через `value.astimezone(timezone.utc)`.

**В чём проблема.** Для значений у границ `datetime`, например
`0001-01-01T00:00:00+05:00`, перевод в UTC выходит за год 1 и бросает
`OverflowError`. Это не `ValueError`, поэтому Pydantic его не перехватывает:
исключение проходит через FastAPI, и на корректно оформленный, но бессмысленный ввод
клиент получает `500 Internal Server Error`. Ошибку нашла дымовая проверка P2. Модель
в P2 сама указала на это место в списке «что проверить на ревью», но не исправила.
Промпт разрешал менять файлы P1 только в крайнем случае, и модель сочла, что такие
значения «отсекаются раньше», хотя валидация схемы срабатывает до любой проверки
сервисного слоя.

**Как исправил.** `_to_utc` превращает `OverflowError` в `ValueError`, и клиент
получает обычный ответ 422 с понятным сообщением. Регрессионный тест:
`tests/test_review_regressions.py::test_02_extreme_datetime_is_422_not_500`. До
исправления он падал, после проходит.

## 3. Можно «отменить» приём, который уже прошёл

**Что сгенерировал ИИ.** `change_status` в `app/services/appointments.py` (P2)
разрешает администратору и регистратору переход `scheduled → cancelled` в любой
момент. Ограничение по времени есть только у пациента: не позже чем за 2 часа.

**В чём проблема.** Модель выполнила промпт буквально. В правиле П7 я не написал,
что отменить можно только ещё не начавшийся приём, и это пробел постановки, а не
ошибка модели. Последствие: если пациент не пришёл, а врач не отметил `no_show`,
регистратор на следующий день может «отменить» прошедшую запись. Неявка исчезает из
статистики (аналитика клиники считает долю `no_show`), а слот в прошлом
освобождается задним числом.

**Как исправил.** Отмена разрешена только до начала приёма для всех ролей. После
начала доступны только `completed` и `no_show`, иначе возвращается 422 с
пояснением. Регрессионный тест:
`test_03_started_appointment_cannot_be_cancelled`. До исправления он падал, после
проходит. Вывод для промптов: перечислять разрешённые переходы мало, нужно
указывать и условия, при которых переход допустим.

## 4. Двойная запись к врачу при одновременных запросах (SQLite)

**Что сгенерировал ИИ.** По правилу П6 из промпта модель защищает проверку
пересечений блокировкой строки врача `SELECT ... FOR UPDATE`, а последней защитой
служит частичный уникальный индекс `(doctor_id, starts_at)`. В допущениях она честно
написала, что в SQLite `FOR UPDATE` ничего не делает.

**В чём проблема.** При этом `app/config.py` из P1 допускает SQLite как рабочую БД
(`sqlite+aiosqlite` в `ALLOWED_DB_DRIVERS`), и на ней защиты от гонки нет совсем.
Два одновременных запроса на 10:00–11:00 и 10:30–11:00 к одному врачу оба получают
`201`. Проверки пересечения в обоих запросах выполняются до вставки, а индекс ловит
только совпадающее начало. Воспроизводится стабильно: три запуска из трёх, тест
`test_04_concurrent_overlapping_bookings_one_wins` до исправления падал с
`[201, 201]`.

**Как исправил.** Добавил `_lock_row`: в SQLite он выполняет пустой
`UPDATE ... SET id = id` по строке врача (при создании) или записи (при переносе и
смене статуса). Этот UPDATE открывает пишущую транзакцию и держит блокировку базы до
commit, поэтому второй запрос ждёт первый и затем видит его запись. В PostgreSQL
функция ничего не делает, там остаётся `FOR UPDATE`. После исправления тест
стабильно даёт `[201, 409]` и ровно одну активную запись.

## 5. Поведение SQL зависит от того, какой модуль импортирован

**Что сгенерировал ИИ.** Поиск без учёта регистра (P3) сравнивает строки через
`lower()`. Встроенный `lower()` в SQLite понимает только ASCII, поэтому модель
добавила в `app/services/dbutil.py` глобальный обработчик
`@event.listens_for(Engine, "connect")`, который подменяет `lower` на Python-версию в
каждом SQLite-соединении процесса. Ошибку регистрации обработчик молча
проглатывал (`except Exception: return`).

**В чём проблема.** Это неявная связь через импорт: подмена работает, только если
кто-то уже импортировал `dbutil`. Приложение импортирует его через роутеры, а скрипт
заполнения БД или миграция, импортирующие только `app.db` и `app.models`, получают
другую семантику того же SQL. Проверка в отдельном процессе:

```text
только app.db:             lower('ИВАНОВ') = ИВАНОВ
app.db + services.dbutil:  lower('ИВАНОВ') = иванов
```

Вдобавок обработчик на классе `Engine` влияет на все движки в процессе, в том числе
чужие, а при сбое регистрации поиск по кириллице тихо перестаёт работать.

**Как исправил.** Регистрация перенесена в `app.db.create_engine` рядом с
`PRAGMA foreign_keys=ON`: она явная и действует только на движок приложения, а ошибка
больше не проглатывается. Глобальный обработчик удалён. Регрессионный тест
`test_05_sqlite_unicode_lower_does_not_depend_on_imports` запускает отдельный процесс,
импортирующий только `app.db`. До исправления он падал, после проходит.
